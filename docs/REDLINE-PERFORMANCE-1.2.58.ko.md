# Cluster Redline 1.2.58 코드·성능 확인

Linux x64, Node v24.22.1에서 실제 앱의 HUD·클러스터 캐시 렌더러를 실행한 결과입니다. 차량의 CPU/GPU, SOME/IP, 소켓 전송, PNG 업로드, 전체 앱 메모리는 이 측정에 포함하지 않습니다.

각 조건 1,500회, 합계 4,500회 반복했습니다. 100회 예열 후 시작하고 250회마다 강제 GC를 수행했으며, 그 비용도 CPU 시간에 포함합니다. 한 회에 HUD와 클러스터를 모두 그립니다.

| 조건 | CPU ms/회 | 경과 ms/회 | JS 힙 시작→끝 MB | 종료 RSS MB | 렌더 캐시 합계 MB |
|---|---:|---:|---:|---:|---:|
| 화면 유지 | 0.614 | 0.529 | 8.47 → 8.53 | 66.95 | 8.18 |
| RPM 매번 변경 | 8.433 | 7.95 | 8.67 → 8.75 | 82.62 | 8.18 |
| RPM·길안내 매번 변경 | 9.248 | 9.004 | 8.85 → 8.91 | 83.9 | 8.31 |

측정 구간에서 강제 GC 후 힙이 계속 증가하는 패턴은 보이지 않았습니다. 네이티브 버퍼와 메모리 할당자의 보유분 때문에 RSS는 힙보다 큽니다. 짧은 호스트 렌더링 측정으로 실차 장시간 메모리 누수나 CPU 사용률을 확정할 수는 없습니다.

## 검토와 수정

- 로그 수집 숨김 메뉴·수집기·보관 코드와 교통 표지 설정·입력·그리기 코드를 제거했습니다. 기존 on 플래그나 즐겨찾기로 재활성화되지 않습니다.
- 오류 기록은 출력할 때만 8개로 잘랐으나 내부 배열은 계속 늘어날 수 있었습니다. 내부도 최근 8개, 각 320자로 제한했습니다. 파일 기록은 하지 않습니다.
- GPU 호스트가 요청한 2 fps보다 빠르게 설정 화면 루프를 호출할 수 있어, 주기적인 상태 갱신을 앱에서도 500ms 간격으로 제한했습니다. 60 Hz 호출 120회에서 갱신 4회, 버튼 조작 즉시 갱신을 테스트했습니다.
- worker 타이머는 한 개이며 종료 시 해제합니다. 구독 세대 번호·읽기 중복 차단·종료 후 늦은 응답 무시, 렌더 요청 병합, 업로드 역압력, 변경 없는 요소 재사용 테스트가 통과했습니다. 검토·테스트 범위에서 무한 재귀나 무제한 요청 큐는 발견하지 못했습니다.

## 재실행

```sh
node --expose-gc tools/cluster-redline-benchmark.js <빌드-stage> 1500
```
